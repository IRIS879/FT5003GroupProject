# Forum Builder Fund DAO（论坛建设基金 DAO）MVP 治理规则

## 一、治理目标

- Forum Builder Fund DAO 是面向高质量内容社区或开发者论坛的社区建设基金治理机制。
- 论坛按固定周期设立一笔公共预算，资金来源可包括赞助、广告收入或会员费。
- 该笔资金统一存放于 DAO Treasury 智能合约中，不由单一站长或管理员个人直接控制。
- DAO 的治理目标是：由真实贡献者共同决定有限社区资金的分配方式，并由智能合约根据治理结果自动执行拨款。
- 资助范围包括但不限于：
  - 开发论坛插件、工具或数据分析功能；
  - 撰写高质量专题内容或研究文章；
  - 维护知识库、文档系统或社区公共资源；
  - 组织社区活动、技术分享或论坛建设项目。

## 二、成员资格与白名单管理

- 仅白名单成员有资格提交提案和参与投票。
- 白名单成员应为论坛中的真实贡献者，原则上需满足以下至少一项条件：
  - 在论坛中持续活跃满 3 个月；
  - 具有持续内容贡献、技术贡献或社区组织记录；
  - 经版主团队或核心委员会审核通过。
- 白名单由 **5 人核心委员会** 管理，采用 **3/5 多签机制** 进行新增、暂停或移除操作。
- 白名单设立的主要目的在于：
  - 防止机器人、水军账号和无关地址进入治理流程；
  - 降低 Sybil attack、刷号投票和垃圾提案风险；
  - 保证治理参与者与论坛公共利益具有真实关联。
- 白名单应为可更新机制，以便纳入新的真实贡献者，并及时处理恶意或违规成员。

## 三、活跃成员（Active Members）定义

- 为避免长期不参与治理的成员抬高法定参与门槛，系统以“活跃成员”作为 quorum 的计算基数。
- 活跃成员定义为：在最近 **2 个 funding round** 中，至少参与过 **1 次有效投票** 的白名单成员。
- 连续 **3 个 funding round** 未参与投票的白名单成员，可被标记为 `inactive`。
- `inactive` 成员暂不计入 quorum 的计算基数，但不当然永久丧失白名单资格；其后续可通过重新参与投票或申请恢复 active 状态。

## 四、Funding Round 制度

- DAO 采用固定周期的 funding round 机制进行治理，原则上每 **30 天** 为一轮。
- 每轮治理流程如下：
  - 提案提交期：**7 天**
  - 形式审查期：**3 天**
  - 投票期：**5 天**
  - 结果确认期：**2 天**
  - 自动执行期：**2 天内完成**
- 每轮设定固定预算，例如 **5,000 USDC**。
- 单个提案申请金额不得超过本轮预算的 **20%**，即在上述示例下不超过 **1,000 USDC**。
- 采用 funding round 的原因在于：
  - 避免先到先得导致预算被较早耗尽；
  - 便于社区在同一轮中比较多个提案；
  - 更符合有限预算下的优先级分配逻辑。

## 五、提案提交规则

- 每位白名单成员每轮最多提交 **1 项提案**。
- 每项提案必须至少包含以下内容：
  - 提案标题；
  - 资金用途；
  - 申请金额；
  - 收款地址；
  - 项目简要说明；
  - 预期交付成果；
  - 预期对社区的价值。
- 提案提交时，提案人需锁定 **50 USDC** 作为可退还押金。
- 押金处理规则如下：
  - 提案通过形式审查并正常完成治理流程的，押金全额退还；
  - 提案被认定为恶意、虚假、重复刷提案或明显不符合基本要求的，押金可被部分或全部扣除。
- 提案押金的目的在于减少垃圾提案，提高治理效率，而非人为抬高参与门槛。

## 六、形式审查规则

- 形式审查仅检查提案是否满足最低合规要求，不对提案优劣进行实质性判断。
- 审查内容包括：
  - 信息是否完整；
  - 收款地址是否有效；
  - 申请金额是否超过上限；
  - 提案内容是否明显违法、恶意或与论坛公共建设无关。
- 通过形式审查的提案方可进入投票阶段。
- 未通过形式审查的提案不得进入投票，并按规则处理押金。

## 七、投票机制

- 仅活跃白名单成员可进行有效投票。
- 提案人不得对自己的提案投票。
- 每位投票人每轮最多可支持 **3 个提案**，并采用排序投票机制：
  - 第一选择记 **3 分**
  - 第二选择记 **2 分**
  - 第三选择记 **1 分**
- 投票期间公开的信息包括：
  - 提案内容；
  - 投票规则；
  - 本轮预算上限；
  - 投票结束后的最终汇总结果与执行记录。
- 为降低拉票、人情票和中途操纵风险，投票期间不实时公开个人投票内容，仅在投票结束后统一公布汇总结果。
- MVP 阶段可采用 `delayed reveal` 或简化版 `commit-reveal` 机制，以兼顾可实现性与投票独立性。

## 八、法定参与门槛（Quorum）

- 每轮投票须满足以下 quorum 条件，治理结果方为有效：
  - 有效投票人数达到活跃成员总数的 **40% 及以上**；
  - 且有效投票人数不得少于 **8 人**。
- 若某轮投票未达到 quorum，则该轮结果无效，该轮预算不执行拨付，可顺延至下一轮重新安排。
- 上述 quorum 设计旨在兼顾治理代表性与中小社区的实际参与能力。

## 九、通过门槛（Approval Threshold）

- 单个提案要进入资助候选名单，至少应满足以下条件：
  - 该提案至少出现在 **30% 的有效选票** 中。
- 只有达到该通过门槛的提案，方可进入后续排序与预算分配阶段。
- 该门槛用于确保提案获得了相对广泛而非零散的社区支持。

## 十、排序与预算分配规则

- 所有达到通过门槛的提案，按照总得分从高到低统一排序。
- 若出现平票，则按照以下顺序进行处理：
  - 获得支持人数较多者优先；
  - 申请金额较低者优先；
  - 提交时间较早者优先。
- 系统按照排序结果依次拨款，直至本轮预算用尽。
- 若某项提案申请金额高于当轮剩余预算，则该提案本轮不执行，可在下一轮重新提交或重新评估。
- MVP 阶段原则上不进行部分拨款，以保持规则简单、明确、易于实现。
- 该机制本质上属于固定预算约束下的竞赛式分配机制，即在有限资源条件下，由社区决定应优先资助哪些提案。

## 十一、Treasury 自动执行规则

- DAO Treasury 由智能合约统一管理。
- 在满足以下条件后，提案可自动执行拨款：
  - 所在轮次已达到 quorum；
  - 提案已达到 approval threshold；
  - 提案经排序后处于本轮预算覆盖范围内。
- 智能合约自动将资金拨付至提案指定的收款地址，无需管理员进行事后人工批准。
- 每个提案的状态至少包括：
  - `Submitted`
  - `Voting`
  - `Approved`
  - `Rejected`
  - `Executed`
- 合约必须防止重复执行和重复拨款。

## 十二、反滥用与治理纪律

- 以下行为视为治理滥用：
  - 恶意刷提案；
  - 利用关联账号操纵投票；
  - 提交虚假或误导性信息；
  - 未披露重大利益冲突；
  - 利用治理漏洞重复领取资金。
- 对上述行为，可根据情节采取以下措施：
  - 扣除部分或全部押金；
  - 取消本轮提案资格；
  - 暂停或移出白名单；
  - 将处理结果记录在治理系统中。
- 若提案执行后被发现存在严重欺诈或明显违背承诺的行为，可由后续治理程序决定是否采取追加限制或追责措施。

## 十三、透明度与审计原则

- DAO 应确保以下信息对成员公开且可审计：
  - 每轮预算规模；
  - 提案内容；
  - 投票规则；
  - 最终投票结果；
  - Treasury 拨款记录；
  - 白名单管理更新记录。
- 为兼顾治理质量与反操纵需求，系统不要求在投票进行期间实时公开个人投票选择，但应确保最终结果可验证、可追溯。

## 十四、MVP 设计原则

- MVP 阶段优先追求规则清晰、逻辑完整和可执行性。
- MVP 不强制引入 NFT、复杂声誉系统或高复杂度链上身份机制。
- MVP 的核心实现模块包括：
  - 白名单成员管理；
  - 提案提交与押金机制；
  - funding round 管理；
  - 投票与门槛判断；
  - 排序与预算约束分配；
  - Treasury 自动执行与状态记录。
